# remnawave-api-go

Go SDK для Remnawave panel API, полностью сгенерированный из OpenAPI-спеки через [ogen](https://github.com/ogen-go/ogen). Это форк `Jolymmiles/remnawave-api-go`, переехавший на собственную идентичность (`github.com/tesum/remnawave-api-go/v3`).

## Что это и как устроено

- `api/` — весь код сгенерирован, **руками не редактируется**. Файлы `oas_*_gen.go` — чистый вывод ogen. `client_ext.go` — тоже генерируется, но собственным скриптом (`scripts/generate_client_ext.py` / логика внутри `pipeline.py`), он оборачивает сырой ogen-клиент в удобные суб-клиенты (`client.Users().GetUserById(...)` вместо `client.UsersGetUserById(...)`).
- `specs/` — OpenAPI JSON-спеки панели по версиям. `<version>.json` — как есть с панели, `<version>-final.json` — после прогона через пайплайн (консолидация схем, патчи, unify error responses и т.д.). Оба коммитятся.
- `scripts/pipeline.py` — единственная точка входа для регенерации: `python3 scripts/pipeline.py specs/<version>.json`. Делает всё: smart-consolidate схем → патчи спеки → `ogen` → генерация `client_ext.go`.
- `scripts/smart_consolidate.py` — тяжёлая логика трансформации спеки (дедуп схем, унификация error-ответов, экстракция inline-схем и т.д.), вызывается из `pipeline.py`.
- `.ogen.yml` — конфиг ogen. `ignore_not_implemented` там **не косметика** — без него генерация падает намертво на реальных спеках панели (см. ниже).

## Как обновить SDK под новую версию API

1. Получить `openapi.json` актуальной версии панели (авто-URL для этого нет — эндпоинт неизвестен/непубличен, спеку каждый раз дают руками через файл или ссылку от пользователя. **Не гадай URL**).
2. `cp <файл> specs/<version>.json`
3. `PYTHONIOENCODING=utf-8 python3 scripts/pipeline.py specs/<version>.json` (на Windows без `PYTHONIOENCODING=utf-8` скрипт падает с `UnicodeEncodeError` на юникодных ✓/✗/→ в выводе — это просто консоль cp1252, не баг пайплайна).
4. `go build ./... && go vet ./... && go test ./...`
5. `gofmt -l api/*.go` — см. секцию про CRLF ниже, не пугайся ложных срабатываний.
6. Обновить `examples/` и `readme.md`, если поменялась публичная сигнатура методов (see "Известные breaking changes" ниже — они бывают на каждый мажорный апдейт панели).
7. Коммит только через PR (branch protection, см. ниже), смержить, затем тегировать.

## Ловушки ogen-генерации (наступали лично, каждая стоила времени)

Все три пункта ниже — это **исправления в `scripts/pipeline.py` / `scripts/smart_consolidate.py`**, не ручные патчи сгенерённого кода. Ручной патч сгенерённого файла **всегда** теряется при следующей регенерации — так уже один раз случилось (см. git-историю `NotFoundError`/error schemas ниже), не повторяй эту ошибку.

### 1. "complex anyOf" ломает генерацию целиком
Ogen не умеет `anyOf` из разных `object`-веток (полиморфные Xray inbound/transport/security-конфиги — легитимно сложный случай, это реальное ограничение генератора, не баг). `.ogen.yml` содержит `ignore_not_implemented: [..., "complex anyOf"]`, чтобы ogen **пропускал** такие операции вместо падения всей генерации — теряется штучно 1 операция (на 3.2.3 это был raw-subscription с сырыми Xray-конфигами), а не всё разом.

Но часть "complex anyOf" — это **не полиморфизм**, а `anyOf` из двух `string`-веток, различающихся только `format` (например `ip: anyOf[ipv4-string, ipv6-string]`). Такое ogen тоже не умеет разруливать, хотя семантически это просто строка. `fix_string_anyof()` в `pipeline.py` схлопывает такие anyOf в обычный `type: string`, теряя строгую типизацию формата, но сохраняя операцию рабочей. Если после апдейта спеки генерация опять падает на "complex anyOf" — сначала проверь, это реальный полиморфизм (тогда просто теряем операцию через ignore) или очередной string-only anyOf (тогда патчи `fix_string_anyof`).

### 2. Ogen не умеет query-параметры вида `array<object>`
Начиная с 3.2.3 панель добавила TanStack-table-style фильтры (`filters`, `sorting`) как query-параметры — массив объектов `{id, value}` / `{id, desc}`. Ogen на это падает с `nested objects not allowed`. `fix_object_array_query_params()` в `pipeline.py` даунгрейдит такие параметры до `type: string` — вызывающий код должен сам JSON-encode'ить значение перед передачей (так же ждёт и бэкенд на самом деле).

### 3. Error-схемы (`NotFoundError`, `BadRequestError`, `UnauthorizedError`, `ForbiddenError`, `InternalServerError`) — **не из спеки, хардкод в пайплайне**
Это единственные схемы, которые пайплайн **изобретает сам**, а не берёт из спеки — см. `ERROR_SCHEMAS` в `unify_error_responses()` (`scripts/smart_consolidate.py`). Причина: панель возвращает 400/401/403/404/500 с разными inline-схемами на каждый эндпоинт, пайплайн unify'ит их в 5 общих Go-типов ради эргономики.

**Критически важно:** в этом словаре обязательным должно быть только `message`. Всё остальное (`timestamp`, `path`, `errorCode`, `statusCode`, `errors`) — опционально. Причина: реальный конверт ошибок NestJS в панели — `{timestamp, path, message, errorCode}`, `statusCode` там **не существует вообще** (это поле легаси-формата и живёт только в отдельной `RemnawaveValidationErrorDto` для 400-валидации). Если сделать `statusCode` обязательным (как было по умолчанию из очень старой версии пайплайна), а панель пришлёт тело без него (например `DELETE` на уже удалённого юзера) — ogen'овский `Decode()` падает с generic `*validate.Error` вместо типизированного `*NotFoundError`, и вызывающий код не может штатно отличить "уже удалён" от реальной ошибки.

Это уже дважды кусало продакшен (консьюмер `iki-backend` из-за этого раньше вообще обходил SDK и делал сырые HTTP-запросы). Первый раз пофиксили точечным патчем сгенерённого `.go`-файла (коммит `b61831c`, для v2.6.1) — патч не тронул сам генератор, поэтому потерялся при следующей полной регенерации (v3.2.3) и баг вернулся. Второй раз пофиксили правильно — в `smart_consolidate.py`, переживёт любую регенерацию. **Если этот баг всплывёт снова — значит кто-то опять хардкоднул required-поля прямо в `ERROR_SCHEMAS`, не патчи вывод, чини словарь.**

### Windows-специфика
- `PYTHONIOENCODING=utf-8` перед `python3 scripts/pipeline.py` — иначе `UnicodeEncodeError` на выводе с юникодными иконками (cp1252-консоль).
- `core.autocrlf=true` в git на Windows означает, что `gofmt -l` на локальной рабочей копии **почти всегда** покажет "не отформатировано" на файлах, которые ты вообще не трогал — это ложное срабатывание из-за CRLF, не реальная проблема форматирования. Проверяй так:
  ```
  git show HEAD:path/to/file.go > /tmp/check.go && gofmt -l /tmp/check.go
  ```
  Если тут пусто — файл реально чистый, значит проблема была только в CRLF рабочей копии, коммитить нечего.
- `generate_client_ext()` в `pipeline.py` теперь сама гоняет `gofmt -w` на сгенерённом `client_ext.go` в конце (было не так — до этого генератор писал невыровненные структуры, и это ловилось только на CI после мержа CI/CD, пришлось чинить отдельным PR). Если когда-нибудь уберёшь этот шаг — вернётся баг с невыровненными полями структур.

## Версионирование — тоже нетривиально

Теги SDK **не следуют обычному Go semver** сами по себе — они привязаны к версии панели API (`v3.2.3`, `v2.8.0`, ...), а суффикс `-N` (`v3.2.3-1`, `v2.3.0-6`, `v2.2.6-1`) означает "N-я итерация SDK для той же версии API" (например багфикс без изменения апстрим-спеки). **Никогда не двигай/не force-push'уй уже опубликованный тег** — Go modules immutable по контракту, у кого-то может быть закэширован checksum на старое содержимое, force-move сломает ему сборку. Для повторного релиза на ту же версию API — всегда новый `-N` тег, никогда не трогай существующий.

### Module path и мажорная версия — почему `/v3`, а не `/v2`
До PR #6 модуль назывался `github.com/Jolymmiles/remnawave-api-go/v2` (неотфорканный путь оригинала) — это ломало `go get github.com/tesum/remnawave-api-go/v2@...` сразу двумя независимыми способами:
1. **Mismatched module path** — заявленный в `go.mod` путь не совпадал с путём, откуда его тянут.
2. **Invalid version** — путь модуля кончается на `/v2`, значит по правилам Go (major version suffix) валидны только теги `v2.x.y`. А теги здесь следуют версии панели (`v3.2.3` и т.д.), т.е. с переходом панели на мажор 3 все новые теги автоматически стали невалидны для `/v2`-модуля.

Решение (PR #6): переименовали модуль в `github.com/tesum/remnawave-api-go/v3` — прямо в `go.mod`, без переноса кода в поддиректорию `v3/` (этот репо никогда не использовал `v2/`-поддиректорию и для исходного `/v2`, так что паттерн просто продолжили). **При следующем мажорном скачке версии панели (4.x, 5.x...) суффикс `go.mod` надо бампать в лок-степ** (`/v3` → `/v4`), иначе новые теги снова станут нерезолвящимися через `go get @tag` (это не разовая проблема, а системная — тег = версия API, значит суффикс модуля обязан следовать за тем же числом).

Старые теги (`v2.2.6-1` … `v2.8.0`) остаются рабочими только через оригинальный путь `github.com/Jolymmiles/remnawave-api-go/v2` — они заморожены на старом содержимом `go.mod` и retag'ать их бессмысленно (см. правило immutability выше). Табличка версий в `readme.md` это явно документирует.

## CI/CD

- `.github/workflows/ci.yml` — build/vet/gofmt-check/test + golangci-lint на каждый push в `main` и каждый PR.
  - golangci-lint настроен на `install-mode: goinstall` **специально**, не просто так — прибитый бинарник из `version: latest` у `golangci-lint-action` собран старым Go-тулчейном и падает с "the Go language version (go1.24) used to build golangci-lint is lower than the targeted Go version (1.25)", если у модуля `go 1.25` в `go.mod`. `goinstall` компилирует линтер тем же тулчейном, что и раннер — обходит проблему.
  - Из-за этого же `install-mode: goinstall` резолвит `@latest` без версионного suffix'а `/v2` в пути линтера — то есть тянет последний **v1.x** golangci-lint, не v2.x. Поэтому `.golangci.yml` написан под v1-схему конфига (без `version: "2"` и `linters.default` — это v2-only ключи, на v1 они валятся с `jsonschema` ошибкой).
- `.github/workflows/codeql.yml` — CodeQL на push/PR в `main` + еженедельно по расписанию.
- `.github/workflows/release.yml` — триггерится на push тега `v*`: пересобирает+тестирует как гейт, потом публикует GitHub Release с авто-генерируемыми notes (diff от предыдущего тега).
- `.github/dependabot.yml` — еженедельные апдейты `go.mod` и версий GitHub Actions.
- `.golangci.yml` исключает сгенерённые файлы (`exclude-generated: strict`) — не пытайся линтить `oas_*_gen.go`/`client_ext.go`, там нет смысла.

### Branch protection на `main`
Включён ruleset "Main" — требует 1 approving review + code-owner review, запрещает force-push/delete/non-fast-forward. Также ruleset "Safe tags" ограничивает создание тегов напрямую. **Как владелец репо ты можешь байпасить оба** (`current_user_can_bypass: always`), но это осознанный шаг, не default: обычный воркфлоу — PR → CI зелёный → либо реальный review, либо `gh pr merge --admin` при сольном мейнтейнерстве. Для тегов аналогично: `git push origin vX.Y.Z` от владельца репо проходит с warning "Bypassed rule violations" — это ожидаемо, не ошибка.

## Известные breaking changes между версиями панели (для памяти при будущих апдейтах)

При переходе 2.8.0 → 3.2.3 панель поменяла:
- Идентификация юзера: UUID → числовой `ID` (`GetUserByUuid` пропал, появился `GetUserById` + `ResolveUser` для поиска по uuid/shortUuid/username).
- Nodes CRUD — раньше не генерировался вообще (ломался о "complex anyOf" на `ip: anyOf[ipv4,ipv6]`, см. выше), сейчас полный набор (`GetNodes`/`CreateNode`/`UpdateNode`/`GetNode`/`EnableNode`/`DisableNode`/`ReorderNodes`).

Не факт, что будущие апдейты панели будут ломать ровно то же самое — но стоит ожидать похожего класса изменений (переименования методов, смена типов путевых/query-параметров) и всегда сверять `examples/` + `readme.md` с реальными сигнатурами после регенерации, а не доверять что "просто пересобралось — значит всё ок" (билд может быть зелёным, а примеры — использовать несуществующий метод, как уже было).
